### Les trois points qui commandent la suite

**C1 — bloquant, portefeuille. Les 12 PR Dependabot ouvertes sont rouges et le
resteront.** Confirmé dans cette session sur deux repos indépendants :
`kreadevis` PR #39 et `elya` PR #21 ont `harness-invariants / invariants` en
`fail`, tous les autres checks verts. La cause a deux étages, et le lot 14 n'en
avait vu qu'un :

1. L'étage connu : `HARNESS_READ_TOKEN` n'existe que dans le magasin de secrets
   *Actions*. Vérifié le 2026-09-20 — `gh secret list --app dependabot` est
   **vide sur les 8 repos**. Sur une PR Dependabot le secret vaut la chaîne
   vide, `harness-invariants` retombe sur `github.token` et ne peut pas cloner
   le harnais privé.
2. L'étage nouveau : l'*updater* Dependabot lui-même n'a pas accès au harnais.
   Log du run `35516280690` (deployment, 2026-09-20) :
   `Failed to request additional scope: 403 … Either the repo doesn't exist, or
   Dependabot doesn't have access to it`, puis `Remote response: Repository not
   found.` en boucle. Il essaie de résoudre
   `SelimLBOURAYA/claude-harness/.github/workflows/*@main` comme dépendance
   `github_actions` et échoue avant même d'ouvrir la PR. Même signature sur
   `kreadevis`, `meal-planner-frontend` et `summerize-youtube` : leur dernier
   run sur `develop` est un run Dependabot en échec.

   Poser le secret ne suffit donc pas : il faut aussi que Dependabot ait accès
   au repo privé, ou que `.github/dependabot.yml` cesse de faire surveiller les
   `uses:` du harnais. Réglage GitHub utilisateur, **prérequis de la
   promotion**.

**C2 — majeur. `meal-planner-backend` n'exerce aucune migration, et son test
prétend le contraire.** `src/test/java/com/mealplanner/FlywayMigrationIT.java`
est un `@SpringBootTest @ActiveProfiles("test")` qui asserte l'existence de cinq
tables. Le profil `test` (`src/test/resources/application-test.yaml`) est
`jdbc:h2:mem` avec `ddl-auto: create-drop` et **`flyway.enabled: false`**. Les
tables dont le test constate l'existence sont donc celles qu'Hibernate vient de
générer ; `V1__initial_schema.sql` n'est jamais joué. C'est le contre-exemple
exact de CONVENTIONS §2.5, sous un nom de classe qui affirme le contraire —
un test de ce nom rend le trou plus difficile à voir qu'une absence de test.

Le lot 9 l'avait relevé en *Warning* et renvoyé à mpb lot 13, ce qui est
défendable ; le nom de la classe, lui, ne l'est pas. `kreadevis-backend`
(`PostgresIntegrationTest`, `postgres:17-alpine`, Liquibase actif) et `elya`
(`SchemaMigrationIT`, `postgres:17`, Testcontainers) sont conformes : 2 backends
sur 3.

**C3 — majeur. Les lots 7 à 13 n'ont eu aucune étape sécurité.** Confirmé par
lecture du skill : `lot-audit/SKILL.md` §Step 2 invoque `Skill(security-review)`
sans passer de répertoire, et la commande intégrée revoit « les changements en
cours sur la branche courante » — celle de la **session**, pas du repo audité.
Le §Step 1 a la même faille : `git diff develop...HEAD --stat` sans `-C`. Une
session ouverte dans `claude-harness` qui audite `deployment` a donc audité
`claude-harness`. Le skill prévoit un repli manuel « si le skill est
indisponible » ; ici il n'était pas indisponible, il visait la mauvaise cible,
donc rien n'a signalé la dérive.
